# 方向重构与成熟能力调研

版本：v1.0

## 1. 结论先行

**建议改方向，但不要把项目描述成“重新做一个 AI 跟拍/自动剪辑模型”。**

建议正式项目方案为：

> **让每个用户成为导演：基于多 Agent 协作与可编程 Skill 的开放智能影像系统**(Open Vide Vision)

这个方案有竞争力的前提是：四天内必须展示一个真实可用的 Skill 被加载、被解释、被 Agent 协作执行，并且最终调用 X4 Air/Link 2 的能力或在 Mock 中完整复现调用链。

### 推荐的一句话命题

> 现有 AI 影像产品替用户做决定，ScenePilot 让用户定义决定的规则：用户可以选择、修改和组合摄影 Skills，面向摄影,多个 Agent 根据视频证据生成导演计划，经安全控制后驱动 X4 Air 和 Link 2，并输出可解释、可再次编辑的成片。

## 2. 成熟能力调研

### 2.1 影石和同类产品已经解决的问题

根据影石公开产品页、你们提供的官方开发资料和产品对比资料，可以确认影石产品生态已经涉及：

- 全景拍摄与后期自由取景。
- 运动/人物跟踪、自动构图和智能拍摄辅助。
- 全景内容重构和普通视角导出。
- AI 影像处理、自动剪辑或智能成片方向。
- Link 2 的 AI Tracking、Auto Composition、PTZ、手势和 UVC/SDK 控制。

这意味着以下说法不能作为核心创新：

- “我们实现了 AI 自动跟拍”。
- “我们实现了 AI 自动剪辑”。
- “我们实现了 360 视频转普通视频”。
- “我们能通过 AI 控制云台”。

这些最多是系统能力或 Demo 组件，必须说明你们增加了什么架构层。

### 2.2 行业剪辑工具已经解决的问题

公开产品资料显示：

- 剪映 AI 已经覆盖智能搜索素材、智能解说粗剪、智能镜头分割、自动字幕/音频等方向，并支持多机位、关键帧、专业剪辑。
- Adobe Premiere 已经提供 AI 视频编辑工具和生成式辅助能力。
- DaVinci Resolve 已经提供对象检测、人脸识别、智能重构、AI 跟踪、智能搜索等能力，并支持第三方插件、工作流和 API 集成。

所以“自动找到好片段并导出一个视频”也不是足够强的差异化。你们需要把输出做成：

1. 导演计划，而不是只有最终 MP4。
2. 规则和 Skill，而不是只有固定模板。
3. 多 Agent 的分工、冲突和审批，而不是一次大模型调用。
4. 设备动作和事件证据的对应关系，而不是只对离线素材做描述。

### 2.3 流式视频理解已经有成熟研究基线

VideoLLM-online（CVPR 2024）公开了流式视频大模型方向，核心是持续视频输入、长上下文、异步编码与生成，并报告在 GPU 上进行实时推理。它可以作为你们的研究基线，但不应被包装成你们原创的“实时视频理解模型”。

TimeChat-Online 等工作进一步说明流式视频有大量冗余 token，可以通过差分选择、事件触发和记忆压缩降低成本。你们的 STC 模块应引用为工程化适配或组合创新，并用自己的压缩率和事件召回实验验证效果。

### 2.4 关于 PanoMind 的证据边界

截至本次检索，没有在影石公开官网、公开产品对比页、公开开发者文档或可靠公开搜索结果中找到名为“PanoMind”的可核验产品说明、技术白皮书或公开 API 文档。

因此答辩时不要直接说：

> “影石的 PanoMind 是一个封闭的端到端 Windows 模型。”

除非赛事官方资料明确给出了这个名称和描述。稳妥说法是：

> “现有影像软件和设备生态已经能自动完成不少重构与剪辑任务。我们不与成熟产品拼单点效果，而是在其能力之上提供开放的 Skill、Agent 协作、设备动作审计和用户可编程导演逻辑。”

如果现场官方材料确认 PanoMind 的定义，再把它放入竞品对比表；否则用“现有影石 AI 影像能力”作为事实表述。

## 3. 新方案成立的边界

### 3.1 可以主张的创新

#### A. 可编程导演 Skill

Skill 不是一段宣传 prompt，而是包含以下内容的可执行包：

```text
Skill
  - manifest.yaml        名称、版本、输入、输出、权限
  - intent_schema.json    用户参数结构
  - policy.yaml           触发条件、镜头规则、剪辑规则
  - prompts/              Agent 提示词
  - tools/                允许调用的受控工具
  - validators/           结果校验与安全边界
  - examples/             测试素材与期望结果
```

#### B. 多 Agent 协作

建议只实现 4 个 Agent，避免把“多 Agent”做成多次无意义的 API 调用：

| Agent | 输入 | 输出 | 是否能控设备 |
|---|---|---|---|
| 导演 Agent （拍摄前）| 用户目标、提取Skills、事件时间线 | 导演计划、优先级、冲突裁决 | 否 |
| 摄影指导 Agent （拍摄时）| 导演计划、设备能力、实时主体状态 | 镜头策略、构图、跟踪和设备动作建议 | 否，只能提议 |
| 剪辑 Agent（拍摄后） | 事件、素材证据、Skill 剪辑规则 | 时间线、视角轨迹、字幕和成片计划 | 否 |
| skills管理Agent(人机交互最重要)|提炼语言规范化找合适的skills，并且根据用户需求从云端和本地提取合适的skills指导其他agents，从而指导摄影初学者（人学ai），并且可以相关的非计算机的摄影专家，把他们的建议和方法提炼总结成skills，并可以本地化个性设置和上传到云端进行开源共享，指导其他初学者(ai学人)| 
所有 Agent 输出都进入 `PlanValidator`，再由 `DeviceExecutor` 执行。Agent 之间用结构化 JSON 传递，不使用自然语言互相转发。

#### C. 用户可编程但不需要写代码

用户可以：

- 选择“动作挑战”“旅行纪录”“人物故事”Skill。
- 修改参数：“优先保留成功后的反应”“不要连续使用同一视角”“高潮前保留 3 秒准备过程”。
- 查看规则卡片和动作计划。
- 批准、拒绝或替换某个动作。
- 保存为自己的 Skill。

这比“用户输入一句 prompt”更能证明用户从甲方变成导演。

### 3.2 不能主张的创新

- 不能宣称发明了新的 VideoLLM。
- 不能宣称比影石端侧模型更快、更清晰，除非有严格可重复的对照实验。
- 不能宣称多 Agent 本身就是技术壁垒。
- 不能把“用了 Qwen API”当作创新。
- 不能把固定的三套 prompt 叫作“可编程平台”。必须有 manifest、权限、参数和可执行验证。

## 4. 推荐产品形态

### 4.1 Skill 市场/面板

Demo 只需要 3 个 Skill：

1. `ActionCoach`：跟踪单人动作，动作开始时全身构图，高潮时标记，庆祝时保留反应。
2. `TravelStory`：X4 Air 保留环境全景，Link 2 负责人物近景，按“地点-人物-事件”组成短片。
3. `TeamMoment`：优先多人构图、互动和声音峰值，减少单人连续镜头。

每个 Skill 显示：

- 描述。
- 适用设备。
- 需要的权限。
- 触发事件。
- 镜头规则。
- 剪辑规则。
- 可修改参数。

### 4.2 导演计划视图

必须展示中间产物，不能只播放最终视频：

```text
[14:32:11] 事件：主体进入区域
规则：ActionCoach.enter -> FullBody
建议：Link 2 切换全身构图
证据：track_id=person_1, confidence=0.92
状态：已批准

[14:32:14] 事件：动作强度达到峰值
规则：ActionCoach.peak -> MarkHighlight + X4 Air backup
建议：保留前 3 秒并锁定全景视角
证据：速度峰值、声音峰值、连续 5 帧姿态变化
状态：自动执行
```

这张时间线是项目区别于普通自动剪辑最重要的可视化证据。

## 5. 四天内的最小可行范围

### P0 必须完成

- 3 个可加载的 Skill manifest。
- 1 个导演 Agent、1 个摄影指导 Agent、1 个剪辑 Agent。
- 结构化导演计划和计划校验器。
- Mock X4 Air 和 Mock Link 2 执行器。
- 至少一个真实/预录视频流程。
- Link 2 控制动作或其 Mock 结果可追踪。
- X4 Air 全景重构脚本或其预渲染结果。
- 用户修改规则后重新生成计划。

### P1 建议完成

- 真实 Link 2 UVC + SDK 连接。
- 真实 X4 Air Camera/Media SDK 或 OSC 连接。
- 一个可运行的 `ActionCoach` Skill。
- 事件证据、动作日志和权限审批。
- STC 压缩前后对比。

### P2 不应阻塞主线

- 完整 Skill 在线市场。
- Skill 沙箱执行任意用户代码。
- 自训练 VideoLLM。
- 复杂跨相机身份重识别。
- 全自动实时语音、多轮 Agent 长对话。

## 6. 建议修改原文中的几个表述

### 原表述

> 市面上已有影石 PanoMind 等优秀的端侧 AI 剪辑模型。

### 建议表述

> 影石及行业内已有成熟的全景重构、自动跟拍和 AI 剪辑能力。我们不在四天内重复训练一个更大的端到端模型，而是将这些能力抽象为可组合、可审计、可由用户修改的导演 Skill，并通过多 Agent 生成和执行导演计划。

### 原表述

> 采用有线连接（网线）。

### 建议表述

> Link 2 使用 USB 连接本地边缘电脑输出 UVC 视频并执行低延迟控制；X4 Air 使用桌面 Camera/Media SDK 的 USB 路径，必要时使用官方 OSC Wi-Fi 路径。云服务器不直接连接相机，云端只承担语义理解、策略规划、存储和非实时任务。

### 原表述

> 基于 VideoLLM-online 或直接调用 Qwen API，对视频流进行理解。

### 建议表述

> 百炼 Qwen 是比赛主语义模型；VideoLLM-online 是可选的 GPU 流式理解基线。系统统一通过 `SemanticProvider` 接口接入，两者都输出同一事件 Schema，主线不依赖某个研究模型能否现场部署。

## 7. 推荐答辩结构

1. 先承认成熟产品已经能自动剪辑和跟拍。
2. 说明“自动做得更好”不是四天项目可证明的命题。
3. 演示用户选择或修改一个 Skill。
4. 展示三个 Agent 的结构化协作结果。
5. 展示计划校验器拦截越界设备动作。
6. 展示 Link 2 执行跟拍、X4 Air 保留全景或 Mock 等价过程。
7. 展示导演时间线，给出每个镜头的规则和证据。
8. 修改规则并重新生成结果，证明系统不是一次性黑盒。
9. 最后说明这套架构可接入更多相机、模型和 Skill。

## 8. 最终判断

### 是否应该改方向

**应该改，但要从“做一个更强的 AI 跟拍助手”改成“做一个可执行、可解释、可扩展的 AI 导演 Skill 系统”。**

### 是否保留三个原方向

**保留为底层能力，不再作为三个并列项目。**

### 最大风险

“多 Agent + Skill + 平台”容易变成架构 PPT。必须至少实现一个 Skill 的完整闭环：

```text
加载 Skill
 -> 输入用户参数
 -> 分析视频事件
 -> 生成导演计划
 -> 校验计划
 -> 产生设备动作
 -> 记录证据
 -> 导出视角/剪辑结果
 -> 用户修改 Skill 参数
 -> 重新执行
```

如果做不到这个闭环，应退回“单 Agent + Skill 配置 + 可解释时间线”，不要继续堆 Agent 数量。
