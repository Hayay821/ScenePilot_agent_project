# Bold Maker 赛道一：技术栈与模型使用总览

版本：v1.0  
目标设备：Insta360 X4 Air、Insta360 Link 2  
AI 平台：阿里云百炼、阿里云 ECS/GPU/PAI/OSS  
开发对象：Claude Coding、任务 3 AI 技术负责人、设备接入负责人

## 1. 项目目标

> 方向更新：原来的三个方向不再作为三个独立产品，而是作为一个开放式智能影像系统的三层能力。

推荐项目名称：**ScenePilot：让每个用户成为导演**。  
副标题：**基于多 Agent 协作与可编程 Skill 的智能影像系统**。

原三个方向的重新定位：

| 原方向 | 新系统中的定位 | 是否单独作为产品 |
|---|---|---|
| AI 全景视频智能重构 | 全景素材理解与渲染能力 | 否，作为 `PanoramaReframeSkill` |
| AI 无接触相机控制 | 设备执行器与安全控制能力 | 否，作为 `CameraControlSkill` |
| AI 智能跟拍与自动剪辑 | 导演任务编排、事件理解和成片能力 | 否，作为 `SmartFollowDirectorSkill` |

这样做的原因是：全景重构、AI 跟拍、自动剪辑本身都已有成熟产品或算法。项目不应声称重新发明这些能力，而应证明用户可以组合、修改和复用这些能力。

项目核心闭环：

```text
用户选择/编写 Skill
    -> 多 Agent 读取用户意图与素材上下文
    -> 生成可检查的导演计划
    -> 经安全策略批准后调用相机能力
    -> 形成事件时间线和素材证据
    -> Skill 驱动全景重构、跟拍和剪辑
    -> 用户修改 Skill 或计划并重新执行
```

项目以“用户可以编程自己的导演逻辑”为主线，将三个工作项连接为一个产品闭环：

1. **AI 全景视频智能重构**：从 X4 Air 的 360 度视频中理解主体、动作和事件，自动生成最佳视角轨迹与平面成片。
2. **AI 无接触多设备控制**：通过自然语言、手势和事件规则控制 X4 Air 拍摄，以及 Link 2 的云台、构图、追踪和画质能力。
3. **AI 智能跟拍助手和自动剪辑**：实时判断“拍什么、什么时候拍、怎么拍”，拍摄后判断“保留什么、如何组织、从哪个设备取镜头”。

建议将整个系统命名为：

> **ScenePilot：事件驱动的多相机 AI 导演**

一句话描述：

> 用户只需选择一个拍摄 Skill 或用自然语言修改它，ScenePilot 使用 Link 2 实时跟拍、X4 Air 全景兜底，通过流式视频理解发现关键事件，生成可解释的导演计划，并按用户规则控制拍摄和成片。

## 1.1 竞争定位原则

成熟能力已经覆盖以下基础问题：

- 影石产品和其编辑工具已经覆盖一部分全景重构、自动剪辑和 AI 影像处理。
- Link 2 自身已经具备 AI 追踪、自动构图和云台控制能力。
- 剪映、Adobe Premiere、DaVinci Resolve 等产品已经具备智能搜索、智能重构、自动字幕、对象跟踪或 AI 辅助编辑能力。
- VideoLLM-online 等研究工作已经证明流式视频理解可以通过持续上下文和异步推理实现。

因此我们的项目不应使用“我们首次实现自动跟拍/自动剪辑”或“我们超过 PanoMind 的基础画质/速度”作为卖点。真正的比较维度是：

1. **开放性**：模型、设备适配器、导演规则和 Skill 可以替换。
2. **可编程性**：用户可以修改拍摄和剪辑规则，而不仅是输入一句需求。
3. **可解释性**：每一条设备指令、选片和视角变化都有事件证据与规则来源。
4. **可复用性**：同一个 Skill 可以迁移到不同训练场、设备或拍摄主题。
5. **人机共创**：系统给用户建议，用户能批准、修改或拒绝，不是黑盒自动出片。

## 2. 为什么 X4 Air 与 Link 2 是合理组合

| 设备 | 系统角色 | 官方能力 | 项目中的使用方式 |
|---|---|---|---|
| X4 Air | “不遗漏”的全景主记录机 | 360 度双镜头、六轴陀螺仪、Wi-Fi/BLE/USB-C、桌面 Camera SDK、Media SDK、OSC | 持续记录全景；通过 SDK/OSC 控制拍摄；使用 Media SDK 拼接和导出；AI 在后期决定视角 |
| Link 2 | “立即对准”的实时跟拍机 | USB UVC 视频、两轴云台、AI 追踪、构图、手势、PTZ、曝光/对焦/白平衡、音频 | 为流式模型提供低延迟视频；执行主体跟踪、云台调整、构图切换和无接触控制 |

两者形成互补：Link 2 的云台画面质量和实时性较好，但可能转错方向或丢失主体；X4 Air 不需要瞄准，保留完整空间，可在事后补救和重新构图。

## 3. 系统核心：事件驱动 AI 跟拍导演

不要让大模型逐帧输出云台角度。正确分工是：

- 高频闭环由本地算法完成：主体检测、跟踪、画面中心偏差、PTZ 平滑控制，目标 10 到 30 FPS。
- 中频闭环由事件检测完成：动作开始、动作高潮、主体切换、欢呼、遮挡、离场，目标 1 到 2 FPS 或事件触发。
- 低频闭环由百炼多模态模型完成：理解用户目标、解释事件、选择拍摄策略、形成剪辑计划，通常每 3 到 10 秒或事件发生时调用。

```text
Link 2 UVC / 公共视频 / X4 Air 预览
                 |
                 v
        Frame Ingest + Ring Buffer
                 |
                 v
  STC Adapter: 变化检测 + 去重 + 关键帧选择
        |                         |
        v                         v
 本地跟踪控制环              Qwen-VL 流式语义
 YOLO + ByteTrack              事件与意图
        |                         |
        +------------+------------+
                     v
              Director State Machine
      IDLE / SEARCH / TRACK / RECORD / HIGHLIGHT / RECOVER
             |                       |
             v                       v
      Link 2 PTZ/追踪           X4 Air OSC/SDK
                     |
                     v
         Event Timeline + Clip Manifest
                     |
                     v
       全景重构 + 多机剪辑 + 字幕 + 导出
```

## 4. 模型与算法选型

### 4.1 必选模型

| 模块 | 推荐选择 | 使用位置 | 不负责的事情 |
|---|---|---|---|
| 用户意图与导演决策 | 百炼 Qwen 文本/视觉模型，运行时从账号可用模型列表选择 | 将自然语言转成结构化拍摄目标；根据关键帧与事件决定动作 | 不逐帧控制云台 |
| 图像/视频语义 | 百炼 Qwen-VL 系列可用模型 | 多关键帧理解、动作描述、事件分类、精彩度与叙事价值 | 不处理全部原始帧 |
| 人体/物体检测 | Ultralytics YOLO 小模型或 RT-DETR 小模型 | Link 2 实时画面目标框 | 不做长时间语义记忆 |
| 多目标跟踪 | ByteTrack | 保持主体 ID、计算中心偏差、形成轨迹 | 不决定故事价值 |
| 人体姿态 | MediaPipe Pose 或轻量姿态模型 | 手势、动作幅度、关键动作启发式 | 不作为唯一精彩度依据 |
| 语音识别 | FunASR；无本地环境时使用百炼可用语音服务 | 自然语言命令、欢呼词、字幕 | 不替代声音能量和节拍分析 |

具体模型名不得硬编码为唯一值。通过环境变量配置：

```text
DASHSCOPE_API_KEY=...
DASHSCOPE_BASE_URL=https://dashscope.aliyuncs.com/compatible-mode/v1
QWEN_VL_MODEL=<账号实际可用的视觉模型名>
QWEN_TEXT_MODEL=<账号实际可用的文本模型名>
```

用户提供的旧 Base URL 仍可使用；阿里云官方目前建议有业务空间时优先使用同地域 Workspace 专属域名。API Key 与 endpoint 必须属于同一地域。

### 4.2 VideoLLM-online 的角色

VideoLLM-online 是 CVPR 2024 的流式视频语言模型框架，特点是边接收视频帧边维护上下文，并行视频编码、LLM 前向和响应生成。公开实现的 8B 模型以 SigLIP 编码帧，通常在 2 到 10 FPS 下推理；项目页报告 RTX 3090 约 5 到 10 FPS、A100 约 10 到 15 FPS。

本项目不应在今晚把它作为唯一主链路，原因是：

- 需要 NVIDIA GPU、CUDA、较大权重和相对复杂的运行环境。
- 原始实现基于 Llama 系模型，与比赛要求的阿里模型生态不是同一主链路。
- 比赛真正需要的是“流式感知架构”，不一定需要原样部署全部权重。

正确用法：

- 今晚：复现其异步思想，使用帧队列、语义任务队列和独立决策任务；底层语义调用百炼 Qwen-VL。
- 明天 GPU 到位：将 VideoLLM-online 作为可插拔 `StreamingSemanticProvider` 基线，测吞吐和延迟。
- 若需要训练：参考官方仓库建议，优先在 Qwen-VL 类模型上做流式数据适配，不要继续投资旧 Llama 文本骨干。

### 4.3 STC 的角色与歧义说明

“STC”在现有信息中没有唯一的论文、仓库或 API 标识，因此实现时将其定义为可替换的 **Streaming Token Compression/Selection** 模块，而不是绑定一个未确认的软件包。

它负责：

1. 丢弃静态、重复和低信息帧。
2. 保留动作变化、主体变化、声音峰值和用户关注对象相关帧。
3. 把连续视频压缩为事件候选与少量关键帧，再调用 Qwen-VL。
4. 维护短期窗口和长期事件摘要，避免把完整历史反复传给模型。

今晚实现的 STC 基线：

```text
输入帧
 -> 缩放到 320/384 像素
 -> 灰度帧差 / SSIM / 直方图差异
 -> 感知哈希去重
 -> 主体框变化与音频能量加权
 -> 每窗口 Top-K 帧
 -> Qwen-VL
```

可参考 TimeChat-Online 的 Differential Token Drop 思路。该论文报告删除 82.8% 视频 token 时仍保留 StreamingBench 上约 98% 性能，但这是论文实验结论，不应直接宣称本项目达到相同效果。项目必须实测“压缩率、事件召回率、API 请求数、平均延迟”。

如果明天赛事方提供明确的 STC 包：只替换 `STCAdapter.select(frames, context) -> SelectedFrames` 的实现，不改变其余架构。

## 5. 三个子系统的接口关系

### 5.1 AI 全景视频智能重构

输入：X4 Air `.insv` 或 Media SDK 导出的等距柱状投影 MP4、事件时间线、目标轨迹。  
输出：带 `yaw/pitch/fov` 的虚拟镜头脚本和 16:9/9:16 成片。

建议镜头脚本：

```json
{
  "source": "x4air_001.insv",
  "shots": [
    {
      "start_ms": 12000,
      "end_ms": 18000,
      "subject_id": "person_1",
      "yaw_keyframes": [[12000, 32.0], [18000, 48.5]],
      "pitch_keyframes": [[12000, -3.0], [18000, 1.5]],
      "fov_keyframes": [[12000, 95.0], [18000, 72.0]],
      "reason": "主体开始冲刺并出现欢呼声"
    }
  ]
}
```

今晚可用 FFmpeg `v360` 滤镜对公开 equirectangular 视频验证；明天优先用官方 Media SDK 完成 `.insv -> mp4` 拼接，再进行虚拟视角渲染。

### 5.2 AI 无接触多设备控制

输入：语音、手势、用户意图、事件。  
输出：受白名单约束的设备命令。

禁止让 LLM 直接拼接并执行任意 SDK/HTTP 命令。模型只能生成结构化 `CameraAction`：

```json
{
  "device": "link2",
  "action": "track_subject",
  "args": {"subject_id": "person_1", "composition": "half_body"},
  "reason": "用户要求跟拍红衣选手",
  "confidence": 0.91,
  "expires_at_ms": 173000
}
```

执行层检查设备能力、状态、参数范围、冷却时间和权限后才能调用 SDK。

### 5.3 AI 智能跟拍和自动剪辑

实时部分输出：主体 ID、设备动作、事件标签、录制区间。  
离线部分输入这些事件，不重新从头盲扫全部视频，从而提高速度和可解释性。

精彩度评分基线：

```text
score = 0.30 * intent_relevance
      + 0.25 * event_intensity
      + 0.15 * image_quality
      + 0.10 * audio_peak
      + 0.10 * story_coverage
      + 0.10 * novelty
```

## 6. 技术栈

| 层 | 技术 | 选择理由 |
|---|---|---|
| 主服务 | Python 3.11、FastAPI、Pydantic | AI/媒体生态成熟，结构化接口清晰 |
| 异步管线 | `asyncio.Queue`，需要跨进程时再用 Redis | 今晚先保持最小依赖，明天可扩展 |
| 视频 | FFmpeg 7、OpenCV、PyAV | 解码、抽帧、音频拆分、转码、全景投影 |
| 本地视觉 | Ultralytics YOLO、ByteTrack、MediaPipe | 实时检测、跟踪与姿态 |
| 模型 API | OpenAI Python SDK 指向百炼兼容 endpoint | 能直接使用用户已有 URL |
| 数据 | SQLite + JSONL | 可追踪事件和模型结果，比赛期间易恢复 |
| 对象存储 | 阿里云 OSS | 原始素材、代理、关键帧和成片 |
| UI | 第一阶段 Streamlit；稳定后 React/Next.js | 今晚快速验证，后续可替换前端 |
| 设备桥 | C++ 独立进程 + 本地 HTTP/WebSocket | 官方 SDK 为 C++，隔离崩溃和 ABI 问题 |
| 部署 | Docker Compose；设备桥在宿主机运行 | 云端服务容器化；USB SDK 不强塞入容器 |

## 8. 评价指标

不要只展示“模型觉得很好”。至少记录：

| 指标 | 定义 | MVP 目标 |
|---|---|---:|
| 事件召回率 | 人工标注关键事件中被系统发现的比例 | >= 80% |
| 高光 Precision@5 | Top 5 片段中人工认可的比例 | >= 60% |
| STC 帧压缩率 | `1 - 入模帧数/采集帧数` | >= 70% |
| 语义响应延迟 | 事件发生到结构化判断完成 | <= 5 秒，云 API 路径 |
| 跟拍丢失率 | 主体存在但 tracker 丢失的帧比例 | <= 10% |
| PTZ 稳定性 | 云台指令反向、振荡、越界次数 | 0 次越界，无持续振荡 |
| 成片闭环时间 | 2 分钟素材到 30 秒预览 | <= 5 分钟 |

## 10. 关键工程判断

1. **主线不是部署一个大模型，而是构建实时感知、设备控制与后期成片闭环。**
2. **百炼 Qwen 是语义大脑，本地模型是眼睛和反射弧，设备 SDK 是执行器。**
3. **X4 Air 与 Link 2 SDK 完全不同，必须用两个适配器。**
4. **VideoLLM-online 是 GPU 基线和架构参考，不是今晚的阻塞依赖。**
5. **STC 先实现为通用压缩接口，待赛事明确具体模块后替换。**
6. **今晚只验证算法闭环，明天才接硬件；两套输入必须实现同一个接口。**
